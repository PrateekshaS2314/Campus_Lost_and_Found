# Campus Lost & Found

A campus lost-and-found application built with Express, EJS, MongoDB, and Mongoose. Students can register a profile, report lost or found items, browse reports, and search lost-item reports. Phase 2 adds claims for found items and listing-owner claim decisions.

## Technologies

- Node.js and Express.js
- EJS server-rendered templates
- MongoDB and Mongoose
- dotenv for local configuration
- HTML and CSS

## Prerequisites

- Node.js 18 or newer and npm
- A MongoDB server, either a local MongoDB installation or a MongoDB Atlas database

## Installation and configuration

1. Install dependencies:

   ```sh
   npm install
   ```

2. Create a `.env` file in the project root by copying `.env.example`, then replace its placeholders with your Atlas database user, password, cluster hostname, and database name:

   ```dotenv
   MONGODB_URI=mongodb+srv://<database-user>:<database-password>@<cluster-hostname>/<database-name>?retryWrites=true&w=majority
   MONGODB_DNS_SERVERS=8.8.8.8,8.8.4.4
   PORT=3000
   ```

   Use the exact hostname and database name in the connection string generated by Atlas. Keep credentials private; `.env` is ignored by Git. `.env.example` contains placeholders only.

3. Ensure your network can reach Atlas and your current public IP is allowed in Atlas **Network Access**.

4. Start the app:

   ```sh
   npm start
   ```

   Run this command from the project root (the directory containing this `package.json`). It executes `node index.js`, which is the Express/Mongoose server and renders the EJS files in `views/`. `src/index.js` is leftover React frontend source and is not used by the `start` or `dev` scripts. Visit <http://localhost:3000> once the server reports a successful database connection.

For Atlas `mongodb+srv://` URIs, the Express server configures Node's DNS resolver before Mongoose connects. The default resolver addresses are Google Public DNS (`8.8.8.8,8.8.4.4`), which can be overridden with `MONGODB_DNS_SERVERS` as a comma-separated list of DNS server IP addresses. This setting affects DNS lookups made by this Node server process only (not Windows or other applications). Use DNS servers reachable from your network; some campus networks/VPNs block external DNS, in which case configure the network's permitted resolver instead. The server preflights Atlas SRV/TXT records and reports the hostname and database name, but never logs the URI or credentials.

For development with Node's built-in file watcher, run `npm run dev`.

## Routes

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/` | Homepage with live report counts and recent reports |
| GET | `/students/new` | Student registration form |
| POST | `/students` | Create a student profile |
| GET | `/students/:id` | View an individual student profile |
| GET | `/lost-items` | Browse and search lost-item reports |
| GET | `/lost-items/new` | Lost-item reporting form |
| POST | `/lost-items` | Create a lost-item report |
| GET | `/lost-items/:id` | View lost-item details |
| GET | `/found-items` | Browse found-item reports |
| GET | `/found-items/new` | Found-item reporting form |
| POST | `/found-items` | Create a found-item report |
| GET | `/found-items/:id` | View found-item details |
| POST | `/found-items/:id/claims` | Submit a claim for a found item |
| GET | `/claims/manage` | Select a student profile and view claims for their found-item listings |
| POST | `/claims/:id/approve` | Approve a pending claim and mark its item as returned |
| POST | `/claims/:id/reject` | Reject a pending claim |

Lost-item search accepts `q`, for example `/lost-items?q=library`, and matches item name, category, and last-seen location.

## Models and relationships

- **Student**: required `fullName`, unique valid `email`, `department`, and `contactNumber`; MongoDB supplies the `_id`.
- **LostItem**: required `itemName`, `category`, `description`, `lastSeenLocation`, `dateLost`, and `reportedBy`; status defaults to `Open`.
- **FoundItem**: required `itemName`, `category`, `description`, `foundLocation`, `dateFound`, and `reportedBy`; status defaults to `Open`.
- **Claim**: required `student`, `foundItem`, and a 10–2000 character `description`; status is `Pending`, `Approved`, or `Rejected` and defaults to `Pending`.

`LostItem.reportedBy` and `FoundItem.reportedBy` are ObjectId references to `Student`. The report forms load registered students from MongoDB for reporter selection. That selection is for attribution only and does not authenticate a student.

`Claim.student` references the student submitting a claim and `Claim.foundItem` references the corresponding found listing. Claims are timestamped. A partial unique MongoDB index allows at most one pending claim from a student for a given found item. Rejected claims are no longer active, so that student may submit another claim while the item remains open. Approval marks the claim `Approved` and the item `Returned`; `Resolved` and `Returned` items cannot receive claims or be approved.

## Claim and return workflow

1. Open an `Open` found-item detail page, select a registered student profile, and provide at least 10 characters explaining why the item belongs to them.
2. The server validates the IDs and records, rejects non-open items and overlong/empty proof, and checks for an existing pending claim. MongoDB's unique partial index also prevents concurrent duplicate pending submissions.
3. To review claims, open **Manage claims** and select the student profile that reported the found item. Pending claims can be approved or rejected.
4. Approval verifies that the selected student owns the found-item listing and that both the claim and item are still pending/open. The claim becomes `Approved` and the item becomes `Returned`. Rejection changes only the claim to `Rejected`.
5. A processed claim cannot be processed again, and an item already returned by another claim cannot be approved a second time.

## Identity and database limitations

This Phase 1/2 application has no login or session-based authentication. The student selector is a demonstration identity mechanism, not secure authentication: a user can submit another student's ID and impersonate the listing owner. Server-side ownership checks ensure the submitted owner ID matches `FoundItem.reportedBy`, but cannot prove who is operating the browser. Do not use this mechanism for real authorization without adding an appropriate authentication system.

Approval uses a MongoDB transaction when the connected deployment supports transactions (for example, a replica set). On standalone MongoDB, it uses conditional updates and attempts to restore the item's `Open` status if the claim update fails. Compensation handles request-time failures but cannot provide the same crash guarantees as a transaction; use a replica-set deployment when atomic multi-document approval is required.

## Validation and error handling

Forms reject missing and whitespace-only values. Student email format and uniqueness are checked; date inputs must be valid calendar dates. Report and claim submissions verify MongoDB ObjectIds and that referenced students/items exist. Claim submissions validate proof length, reject duplicate pending claims, and accept only `Open` found items. Decision POST routes verify owner identity, pending claim status, and an `Open` item for approval. Invalid IDs and missing records render a 404 page (or a clear form error where appropriate); validation and duplicate errors are shown on the relevant form. Unexpected request/database errors are logged on the server and shown to users only as a generic message (no database URI or stack trace is exposed).

## Phase 1 verification checklist

- [ ] Confirm MongoDB is running and `npm start` connects successfully.
- [ ] Register a student, then check that `/students/:id` shows the saved profile.
- [ ] Try registering the same email twice and confirm the duplicate is rejected.
- [ ] Submit both lost and found reports using a registered student.
- [ ] Browse the report lists, open details, and verify reporter information.
- [ ] Search lost reports by item name, category, and location.
- [ ] Check empty states before reports exist, and submit blank, invalid-date, and invalid-reference forms.
- [ ] Open malformed and nonexistent student/item IDs and confirm the 404 response.

You can run the JavaScript syntax and EJS template compilation checks with:

```sh
npm run check
```

## Phase 2 manual verification checklist

The project does not have an automated test runner. With MongoDB running and at least two registered students, verify:

- [ ] Submit a valid claim for an `Open` found item and confirm it appears as `Pending` under **Manage claims** for the listing owner.
- [ ] Submit a second pending claim for the same student/item and confirm it is blocked. Reject the first claim and confirm that the student can submit another while the item remains open.
- [ ] Approve a pending claim as the listing owner and confirm the claim is `Approved`, the item is `Returned`, and its detail page disables further claims.
- [ ] Try to claim a returned item and confirm the server rejects the submission.
- [ ] Reject a pending claim as the listing owner; confirm the claim is `Rejected` and the item remains `Open`.
- [ ] Try to approve or reject using a different student's profile and confirm the server refuses the decision.
- [ ] Try to decide an already processed claim and try to approve a second pending claim after another claim returned the item; both decisions must be refused.
- [ ] Try missing/invalid IDs, unknown students/items/claims, empty/short proof, and proof longer than 2000 characters; verify useful errors without stack traces or database details.
- [ ] Recheck Phase 1 student registration/profiles, lost and found report submission, listing/detail pages, and lost-item search/filtering.

## Demonstration

Start MongoDB, start the app, register at least two student profiles, and use them in the lost-item and found-item report forms. Submit a claim using one profile, then manage the claim as the profile selected as the found listing's reporter. Browse the report lists, item details, and student profiles to demonstrate that content is read from MongoDB rather than hard-coded examples.
